# 红线策略

三档判定，只有**确定性信号**拥有关闭权。

## 一、分层

| 层 | 判定依据 | 动作 | 可配置 |
|---|---|---|---|
| L0 | 无 | 放行 | — |
| L1 | 提交订单 / 确认下单 | 记录 + 提级，不中断 | 是 |
| L2 | 输入凭证 / 点击支付动词 | 暂停 + 人工接管 | 仅 `researchMode` 可降为只记录 |
| L3 | 包名 / 证书 / `CATEGORY_GAME` / `FLAG_SECURE` / 支付 scheme | **终止进程** | **否** |

关键原则：**金额、价格、余额是名词，不触发任何动作。** 付款的唯一不可逆点是"提供凭证"和"点击支付"，两者都在动作层判定。

## 二、动作级拦截

比页面级判定精确得多，也是比价场景零误杀的原因。

| 动作 | 判定 | 结果 |
|---|---|---|
| `Type` 到 hint/label 含密码、验证码、卡号、CVV、身份证、PIN | 凭证索取 | L2 |
| `Tap` 按钮文字含「立即支付 / 确认支付 / 付款 / 去支付 / 指纹支付 / 免密支付」 | 支付动作 | L2 |
| `Tap` 按钮文字含「提交订单 / 立即购买 / 加入购物车」 | 仅提级 | L1（soft） |
| `Tap` / `Swipe` / `Scroll` / `Back` / 截图 | 浏览 | L0 |

`ORDER_ONLY` 提级若 3 步内未出现 L2 信号，自动回落 L0。

## 三、单调升级（不可绕过点）

模型上报的 `risk` **只能把状态推向更保守**：

```
decide(ruleHit, modelRisk):
    ruleHit.hard        -> Kill          // 确定性红线，最高优先
    ruleHit             -> Escalate
    modelRisk != null   -> Escalate      // 永远不能返回 Pass
    else                -> Pass
```

因此即使模型被 prompt injection 诱导、幻觉、或漏检，最坏结果是多暂停一次，**不会漏过 L2**。

## 四、为什么模型不能触发 Kill

屏幕上任何文本都可能被目标 App 控制（评论、商品标题、聊天内容）。
若模型可触发 `Kill`，则**一段文本即可远程杀死用户进程**，构成免费 DoS。

因此：`Kill` 只由确定性代码（包名 / 证书 / `FLAG_SECURE` / scheme）触发。

## 五、fail-closed 清单

以下情况一律按"命中"处理：

- 前台包名解析失败
- `PackageInfo` 读取失败
- `dumpsys window` 输出不可解析
- 截图全黑但无障碍树仍有节点（疑似 secure 窗口）
- 目标 App 身份无法确认

## 六、可观测性

每次 L1/L2/L3 判定写一条结构化日志（时间、包名、规则 id、动作、证据摘要、耗时），
导出为 JSON。这既是调试材料，也是"红线确实生效"的证据。

日志中**不得**落任何凭证明文、完整界面文本或个人信息。
